# Ticket batch

Runs a batch of tickets through `.claude/workflows/ticket-batch-thorough.js` or `ticket-batch-fast.js`. The user's
request to implement the tickets is the opt-in for the Workflow tool; do not ask again unless something below is
unclear. Changing the workflows themselves is covered in section 6.

## 1. Collect the tickets

1. Normalise each name the user gives (drop `.md` and folders). "All tickets in todo" means every file in
   `practice/tally/tickets/todo/`.
2. Find each ticket. It must be in `todo/`, or be a `type::bug` in `backlog/`, or be an approved draft in a folder
   the user names (pass it as `ticketsDir`). Stop and report any ticket that is in another folder, or a non-bug in
   `backlog/` that has no `## Answers` (it needs clarifying first, see `tickets/README.md`).
3. Read each ticket's `ID` and labels. Branch: `fix/<name>` for `type::bug` or a ticket with `## Feedback`,
   otherwise `feat/<name>`. Answers the user gives in chat for a ticket's clarifying questions go into `answers`.
4. Merge order: bugs with `priority::high` first, then tickets others depend on (`Depends on`), then small changes
   before large ones. Keep the user's order if they gave one.

## 2. Choose the shape

- `ticket-batch-thorough` (default): Opus plans the batch; Haiku builds each ticket with unit and API tests
  (Sonnet takes over only when Haiku fails); Sonnet reviews and fixes each ticket as soon as it is built; one Opus
  lead reviews the batch, merges into `develop` and runs the full e2e suite.
- `ticket-batch-fast`: when the user asks for speed, says it is urgent, or says to skip the Sonnet review. No
  per-ticket Sonnet review; one Opus reviewer per chunk of up to 6 tickets, then one Opus lead merges and runs e2e.

## 3. Preconditions

- The main checkout is on `develop` with a clean tree (untracked `.scratch/` and `test-results/` are fine). No
  other batch workflow is running.
- Use today's date in the user's time zone for `date`.

## 4. Run

Call the Workflow tool with `name` set to the chosen workflow and `args`:

```json
{
  "date": "yyyy-mm-dd",
  "tickets": [{ "name": "ticket_name", "id": "TAL-n", "branch": "feat/ticket_name", "answers": "optional" }],
  "ticketsDir": "optional",
  "chunkSize": 6
}
```

Tell the user in two or three lines which tickets run, in which merge order, and which shape. Do not wait while it
runs; a notification arrives when it finishes.

## 5. Report

1. Read the result (or `journal.jsonl` in the run's transcript folder if it is cut off).
2. Verify with git: `git log --format='%h %an <%ae> %ad %s' <baseCommit>..develop` for authors and dates, the
   tickets in `tickets/ready-to-review/`, and a clean `develop`.
3. Report: plan risks, which builds needed Sonnet, review findings and fixes per ticket, the `develop` head, check
   counts, open issues, and what waits for the human (testing the tickets, pushing `develop`). Never push.

## 6. Changing the workflows

The two workflow files are generated. Edit `.claude/workflow-src/ticket-batch.js` (the shared body) or
`.claude/workflow-src/build.mjs` (each workflow's `meta` and `MODE`), then run
`node .claude/workflow-src/build.mjs` from the repository root. Never edit `.claude/workflows/*.js` by hand:
`npm run test:hooks` fails when they differ from the source.

How the progress view groups agents, as observed on 2026-10-30 (`/workflows`):

- An agent appears under the `meta.phases` entry whose `title` equals the `phase` option of its `agent()` call.
- An agent started inside a nested `workflow('<name>', ...)` call appears under one extra group `▸ <name>`, never
  under the parent's phases, even when the titles match. The parent's declared phases then stay at "0 agents".
- A declared phase that no agent uses stays visible as "Not started yet" for the whole run.

Do not split a workflow into a wrapper and a nested workflow to share code. Share code through
`workflow-src/` and the build step instead.

Wrong: a wrapper whose phases never fill.

```js
// ticket-batch-thorough.js
export const meta = { name: 'ticket-batch-thorough', description: '...',
  phases: [{ title: 'Plan' }, { title: 'Build' }, { title: 'Review' }, { title: 'Batch review' }] }
return await workflow('ticket-batch-core', { ...args, mode: 'thorough' })
// View: 1 Plan 0 agents, 2 Build 0 agents, 3 Review 0 agents, 4 Batch review 0 agents,
//       5 ▸ ticket-batch-core 3/5 (every agent is here)
```

Right: the workflow runs its own agents, and its declared phases match its `phase` options.

```js
// ticket-batch-thorough.js (generated by build.mjs)
export const meta = { name: 'ticket-batch-thorough', description: '...',
  phases: [{ title: 'Plan' }, { title: 'Build' }, { title: 'Review' }, { title: 'Batch review' }] }
const MODE = 'thorough'
await agent('...', { label: 'plan', phase: 'Plan', model: 'opus' })
// View: the four declared phases fill one after another (1 Plan, 2 Build, 3 Review, 4 Batch review),
//       and there is no ▸ group for a nested workflow
```

Declare only the phases the workflow can reach. The fast workflow exists to cut steps, so it has fewer phases; do
not add phases to it for symmetry with the thorough one. `build.test.mjs` checks that the declared phases match the
`phase` options each workflow can reach.

- Thorough view: 1 Plan, 2 Build, 3 Review, 4 Batch review.
- Fast view: 1 Plan, 2 Build, 3 Batch review. There is no Sonnet Review step. With more than one chunk, the agent
  that merges all chunks and runs e2e also sits in Batch review.

Before you write how the progress view (or any other tool behaviour) works, check it: read the workflow-authoring
reference, or run the workflow and look at the view. If you have not checked, say so instead of describing it.
